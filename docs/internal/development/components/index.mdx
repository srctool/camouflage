# Components — Overview

## Concept {#concept}

Each note in this folder is a **contract**: what the component takes, what state and slots it hands to the skin's renderer, which tokens a skin should use, and what accessibility it guarantees under *every* skin. Platform notes implement the contract. Skins draw it.

### The v1 set

v0.1 ships the full component set (ADR-40): the original set (ADR-21), CamoPagedList and CamoSkeleton (ADR-29), the date and time pickers, stepper and accordion (ADR-35), every "Later" row of the [Component Inventory](/guide/foundations/component-inventory), and the charts.

Overlays (dialogs, bottom sheets) open through the **platform's navigator**: Flutter `showCamoDialog`/`showCamoBottomSheet`, Compose Navigation 3 entries with Camouflage scene metadata. See [Overlays](/components/overlays/overlays).

### Reviewing a component: API or theme?

- **ADR-23:** a parameter goes into the component API only if every dialect can render it.
- **ADR-28:** a layout or proportion choice that a brand's Figma commonly changes goes into the component theme, with a per-skin default.
- **ADR-30:** for designs that go further (floating, hiding, expanding, reshaped components), offer the cheapest level that covers them: theme option → controlled behavior input → public building blocks → renderer override.

### About the "Material mapping preview" and defaults in component notes

Each component note shows a **Material mapping preview** and **Material defaults** in its component-theme table. Material is the *reference dialect* because its measurements are public and complete. **The v1 skin is Minimal**: its defaults for every component are in one table in [Minimal Skin](/guide/skins/minimal-skin) §3.4, and that's what v1 implements.

### Rules shared by every component

1. **Controlled.** The component never owns the source of truth. Values come in (`checked`, `value`) and changes go out (`onCheckedChange`, `onValueChange`). The only internal state is interaction (pressed/focused/hovered), which is visual.
2. **Camouflage's own vocabulary.** Components with visual variants take `appearance` (`Solid`, `Soft`, `Raised`, `Outline`, `Ghost`, `Link`) and `tone` (`Default`, `Error`, `Success`, `Warning`, `Info`), independently. They never use one design system's private terms (Material's `tonal`, Apple's `borderedProminent`). See [Design Language](/guide/foundations/design-language).
3. **The component owns behavior; the renderer owns visuals.** Callbacks, the semantics role and label, the enabled gate, the minimum touch target (48dp) and focusability are set by the component, so they hold under every skin.
4. **Layout stays with the platform.** No `CamoRow` or `CamoColumn`. Use `Row`/`Column`/`Box` (Compose) or `Row`/`Column`/`Stack` (Flutter), with `Camouflage.spacing` for gaps.
5. **Text is a value, icons are widgets, layout is a slot.** Labels, titles and messages are `String`s the renderer draws. Icons are passed as icon widgets (your `AppIcon.x()`) and follow the icon style the component sets. Nested actions are Camouflage components (dialog buttons, top-bar icon buttons). Only free layout (card, surface, dialog `content`) is a slot. See ADR-12 in [Decisions](/guide/project/decisions).
6. **Platform extras are added at the platform level.** Each platform adds its own conventional parameters (a Kotlin `modifier: Modifier`, a Flutter `key`) on top of the contract.

### How each component note is organised

- §1 Why: what problem the component solves.
- §2 Shape: the render flow for this component, and a Material mapping preview.
- §3 API: the **Contract** (parameters, state, slots), **Tokens used**, and **Accessibility**.

### The component skeleton {#kotlin-the-component-skeleton}

```kotlin
@Composable
public fun CamoButton(
    text: String,
    onClick: () -> Unit,
    modifier: Modifier = Modifier,                         // Compose convention: first optional param
    appearance: Appearance? = null,                         // null → ButtonTheme.defaultAppearance
    tone: Tone = Tone.Default,
    enabled: Boolean = true,
    loading: Boolean = false,
    prefixIcon: (@Composable () -> Unit)? = null,
    suffixIcon: (@Composable () -> Unit)? = null,
    interactionSource: MutableInteractionSource? = null,   // Compose convention: hoistable source
) {
    val skin = requireSkin("CamoButton")                                        // 1. fail fast, named
    val theme = requireTheme("CamoButton")
    val source = interactionSource ?: remember { MutableInteractionSource() }
    val interaction = source.collectInteractionState()                          // 2. pressed/focused/hovered
    val style = remember(skin, theme) { skin.button.defaults(theme).merge(theme.components.button) }   // 3. resolve
    val behavior = modifier                                                      // 4. behavior modifier
        .minimumTouchTarget()
        .clickable(source, indication = null, enabled = enabled, role = Role.Button, onClick = onClick)
        .semantics(mergeDescendants = true) { contentDescription = text }
    skin.button.Render(                                                          // 5. delegate
        state = ButtonState(text, enabled, loading, appearance ?: style.defaultAppearance, tone, interaction, source),
        slots = ButtonSlots(prefixIcon, suffixIcon),
        theme = theme, style = style, modifier = behavior,
    )
}
```

1. **Fail fast** with the component's name ([Provider and Scoping](/guide/architecture/provider-and-scoping#implementation)).
2. **Interaction**: `collectInteractionState()` (a core helper) combines `collectIsPressedAsState`, `collectIsFocusedAsState` and `collectIsHoveredAsState` into `InteractionState`.
3. **Resolve the component style** once per skin/theme change (`remember` keys).
4. **The behavior modifier** does clicks, the role, semantics and the touch target, with `indication = null` because the *renderer* draws the feedback.
5. **Delegate** to the renderer, which applies `behavior` outermost ([Skin Contract](/guide/architecture/skin-contract#implementation)).

### Core helpers every component uses {#kotlin-core-helpers-every-component-uses}

| Helper | What it does |
|---|---|
| `Modifier.minimumTouchTarget(size = 48.dp)` | a layout modifier that reports at least 48×48 and centers the visual content, expanding the pointer area without growing the visuals (the same technique as Material 3's `minimumInteractiveComponentSize`, reimplemented because core doesn't depend on material3) |
| `MutableInteractionSource.collectInteractionState()` | `InteractionState` from the four `collectIs…AsState` flows (pressed, focused, hovered, dragged) |
| `rememberRovingFocus(count)` | one Tab stop per group, arrow keys move (and select, for radios, segments, tabs, chip groups), RTL-aware |
| `Modifier.camoClickable(onClick, enabled, role)` | public: `clickable` + the **active skin's** feedback + the touch target, for an app's own clickable rows. Switching or borrowing skins restyles them too. |
| `rememberHideOnScroll(listState)` | `visible = false` while scrolling down, for the nav bar, top bar and FAB (ADR-30) |
| `ProvideContentStyle(color, iconStyle)` | sets `LocalCamoContentColor` + `LocalCamoIconStyle` for slots |
| `Modifier.camoError(message: String?)` | semantics `error(message)` + a polite live region when the message appears |

### The component skeleton {#dart-the-component-skeleton}

```dart
class CamoButton extends StatefulWidget {
  const CamoButton({
    super.key,
    required this.text,
    required this.onPressed,                    // VoidCallback?; null = disabled (Flutter convention, replaces base `enabled`)
    this.appearance,                            // null → CamoButtonTheme.defaultAppearance
    this.tone = Tone.defaultTone,
    this.loading = false,
    this.prefixIcon,
    this.suffixIcon,
    this.focusNode,                             // Flutter convention: hoistable focus node
  });
  // fields …
  @override
  State<CamoButton> createState() => _CamoButtonState();
}

class _CamoButtonState extends State<CamoButton> {
  bool get _enabled => widget.onPressed != null;
  late final _interaction = CamoInteractionController();              // 1. interaction state

  @override
  Widget build(BuildContext context) {
    final skin = Camouflage.skinOf(context, component: 'CamoButton'); // 2. fail fast, named
    final theme = Camouflage.themeOf(context, component: 'CamoButton');
    final style = skin.button.defaults(theme).merge(theme.components.button);   // 3. resolve
    final visual = skin.button.render(context,                         // 4. delegate
        ButtonState(text: widget.text, enabled: _enabled, loading: widget.loading, appearance: widget.appearance ?? style.defaultAppearance,
                    tone: widget.tone, interaction: _interaction.value, controller: _interaction),
        ButtonSlots(prefixIcon: widget.prefixIcon, suffixIcon: widget.suffixIcon), theme, style);
    return CamoBehavior(                                               // 5. behavior wraps the visual
      controller: _interaction, focusNode: widget.focusNode, enabled: _enabled,
      onActivate: widget.onPressed,
      semantics: (child) => Semantics(button: true, enabled: _enabled, label: widget.text,
                                      excludeSemantics: true, child: child),
      child: CamoTouchTarget(child: visual),
    );
  }

  @override
  void dispose() { _interaction.dispose(); super.dispose(); }
}
```

1. **Interaction** is owned by the component's `State` (`CamoInteractionController`), and listened to by renderers.
2. **Fail fast** with the component's name.
3. **Resolve** the component style.
4. **Delegate** to the renderer (a plain `Widget` comes back).
5. **Wrap** it in the behavior: focus, keyboard activation, hover, press positions, semantics, and the 48 × 48 touch target.

The `ListenableBuilder` around the renderer (so it rebuilds on interaction changes) lives inside `CamoBehavior`.

### Core helpers {#dart-core-helpers}

| Helper | What it does |
|---|---|
| `CamoBehavior` | `FocusableActionDetector` (focus, hover, Enter/Space → `ActivateIntent`) + `GestureDetector` (tap down/up/cancel with local positions → the controller) + semantics builder + `ListenableBuilder` |
| `CamoTouchTarget` | a `SingleChildRenderObjectWidget` that sizes itself to at least 48 × 48 and hit-tests the whole area, while painting the child at its own size (the same technique as Material's `_InputPadding`, reimplemented without Material) |
| `CamoContentStyle` | content color + icon style, plus `IconTheme` and `DefaultTextStyle` for native widgets |
| `CamoRovingFocus` | one Tab stop per group, arrow keys move (and select for radios, segments, tabs, chip groups), RTL-aware |
| `CamoHideOnScroll` | a `ValueNotifier<bool>` over a `ScrollController` for hide-on-scroll bars and FABs (ADR-30) |
| `CamoClickable` | public: `CamoBehavior` + the **active skin's** feedback + the touch target for an app's own tappable rows |
| `CamoErrorSemantics` | wraps a field with `Semantics(validationResult: …)` and announces new errors via `SemanticsService.announce` |

## Web (planned) {#web}

:::info[Status: draft for the W0 spike]

The component contracts in `base/03 - Components` are written as Kotlin signatures (`CamoButton(text, onClick, appearance, tone, enabled, loading, prefixIcon, suffixIcon)`). This note says how every kind of parameter becomes a custom element, so each web component follows the same rules and a parameter is easy to find from the contract. The spike (srctool/camouflage-web#1) tests rules 1 to 8 on the button and the dialog; the input rules (§3.5) are confirmed at W3.

:::

### 1. Why {#web-1-why}

Without shared conventions each component would invent its own attributes, events and slots. Web APIs also differ from Compose and Flutter in ways that matter: values reach elements as **strings** (attributes) or as **JS values** (properties), events are DOM events, and there are no lambdas for content, only slots.

The contract stays the source of truth. This note does not rename anything: a parameter named `supportingText` is `supporting-text` as an attribute and `supportingText` as a property, always.

### 2. Shape {#web-2-shape}

| Contract (Kotlin and Dart) | Web |
|---|---|
| a component `CamoTextField` | a custom element `camo-text-field`, class `CamoTextField`, tag registered by the `define` entry |
| a **value** parameter (`String`, `Boolean`, enum, number) | an **attribute and a property**, kept in sync |
| an **object, list or function** parameter (`inputFilter`, `displayFormat`, `items`, `rules`) | a **property only** |
| a **widget** parameter (`prefixIcon`, `confirm`) | a **named slot** (`slot="prefix-icon"`) |
| a single layout `content: Slot` | the **default slot** |
| a callback `onClick`, `onValueChange` | a **DOM event** (`click`, `input`) or a `camo-*` custom event |
| `modifier` (size, padding, alignment) | CSS on the host element (`class`, `style`) |
| `skin` and `theme` (never parameters) | the provider (context and CSS variables) |

### 3. API {#web-3-api}

#### 3.1 Names {#web-31-names}

| Thing | Rule | Example |
|---|---|---|
| Tag | `camo-` + the component name in kebab-case, without the `Camo` prefix | `CamoSegmentedControl` → `camo-segmented-control` |
| Class | the contract name | `CamoSegmentedControl` |
| Attribute | the parameter in kebab-case | `supportingText` → `supporting-text` |
| Property | the parameter in camelCase, same as the contract | `el.supportingText` |
| Enum value | lowercase kebab-case string | `Appearance.Solid` → `appearance="solid"`, `Tone.Error` → `tone="error"` |
| Slot | the widget parameter in kebab-case | `prefixIcon` → `slot="prefix-icon"` |
| Event | the DOM event if one exists, else `camo-` + kebab-case | `click`, `camo-dismiss` |
| CSS part | named in the component note | `::part(label)` |

#### 3.2 Values: attributes and properties {#web-32-values-attributes-and-properties}

- Primitive values and enums are **both** an attribute and a property. The property is the source of truth; attributes **reflect** only where the value is part of the look or the state (`appearance`, `tone`, `disabled`, `loading`, `selected`, `open`), so styling and tests can select on them.
- **Absent means null.** A nullable parameter (`appearance: Appearance? = null`) is "not set" when the attribute is absent; the theme's default applies. Setting the property to `null` removes the attribute.
- **Booleans default to false.** HTML booleans are present or absent, and cannot be "true by default" cleanly. A contract parameter that defaults to `true` is **inverted**:

| Contract | Web |
|---|---|
| `enabled: Boolean = true` | `disabled` (absent = enabled) |
| `singleLine: Boolean = true` | `multiline` (absent = single line) |
| `loading: Boolean = false` | `loading` |
| `secure: Boolean = false` | `secure` |

- **Text values are attributes, not slot content.** The contract says text is a *value* the renderer draws in its own style (`text`, `label`, `title`, `message`, `placeholder`, `supportingText`, `error`), and a renderer may not inspect a slot. So `<camo-button text="Save">`, not `<camo-button>Save</camo-button>`. This also keeps server rendering simple: the renderer gets the string from an attribute, and the light DOM is not needed to render. Using the default slot as the text is an open question (§5).
- **Numbers** are attributes parsed as numbers and properties as numbers. **Dates and times** are ISO strings (`2026-11-22`, `13:45`, `2026-11-22T13:45`); a range is two properties, `start` and `end`.
- **Objects, lists and functions** are properties only. Frameworks that can't pass properties declaratively set them in code (React 19, Vue, Svelte and Angular can).

#### 3.3 Widgets and content: slots {#web-33-widgets-and-content-slots}

- A widget parameter is a **named slot** in kebab-case: `prefixIcon` → `<camo-icon slot="prefix-icon">`, dialog `confirm` and `dismiss` → `slot="confirm"` and `slot="dismiss"`.
- A single layout content parameter (`content: Slot`) is the **default slot**.
- A skin only decides **where a slot goes** (the renderer places the `<slot>`); it never looks at what is slotted in (the Skin Contract rule). The slot names a component exposes are part of its contract and appear in the Custom Elements Manifest.
- **Icons:** a `camo-icon` takes inline SVG as its child (`<camo-icon><svg …/></camo-icon>`) or a `name` registered with `registerIcons({ plus: "<svg…" })`. It takes its size and color from `--camo-icon-size` and `--camo-content-color`, set by the container.

#### 3.4 Events and callbacks {#web-34-events-and-callbacks}

| Contract | Web |
|---|---|
| `onClick` | the native `click` event. The element handles Enter and Space, and does **not** fire `click` when disabled or loading (it stops the event in the capture phase). |
| `onFocusChanged` | the native `focus` and `blur` events (they don't bubble; `focusin` and `focusout` do) |
| `onValueChange` | `input` while editing and `change` on commit, both native-style; the `detail`-less event reads from `el.value` |
| Other callbacks | a `CustomEvent` named `camo-` + kebab-case, with a typed `detail`, `bubbles: true`, `composed: true` (so it crosses shadow roots) |

Rules: an event is **fired once per user action**; a cancelable event can be cancelled with `preventDefault()`, and the element then keeps its previous state. Event names and `detail` types are listed in the manifest and in the `HTMLElementEventMap` type (section 3.8).

#### 3.5 Inputs, forms and controlled values {#web-35-inputs-forms-and-controlled-values}

The contract's inputs are **controlled** (`value` plus `onValueChange`). On the web:

- `value` is a property and attribute (initial value). The element updates `value` itself when the user edits, and fires a **cancelable** `camo-before-change` (detail `{ value }`) first. Calling `preventDefault()` on it rejects the edit, which gives the same control a controlled input has in Compose and Flutter. Then it fires `input` and, on commit, `change`.
- A framework that wants a fully controlled input sets `value` in response to the event, and nothing else is needed.
- Every input is **form-associated** (`ElementInternals`): it takes `name`, `value`, `required`, `disabled`, takes part in `FormData`, `reset` and `form.checkValidity()`, and reports validity with `setValidity`. A text field shows its `error` attribute (the contract's `error: String?`) as the error state. **Confirmed in W3:** an `error` also makes the input invalid to its form (`customError`), so `form.checkValidity()` and `requestSubmit()` honor it; the user's next edit clears a message the form set.
- `CamoForm` and its form fields: the rules are objects, so `rules` is a **property**, a rule or a list of rules by input `name`. Form-level state is read through events (`camo-submit`, `camo-invalid`, `camo-changed`) and `form.valid` and `form.dirty`. **Confirmed in W3:** every input with a `name` inside the form takes part, so there is no field wrapper; it works with a native `<form>` around it or alone.
- `inputFilter` and `displayFormat` are **properties** (objects with functions), never attributes.

#### 3.6 Overlays {#web-36-overlays}

The base notes open overlays through the platform's navigator (`showCamoDialog` in Flutter, Navigation 3 entries in Compose). The web offers **both** forms:

```html
<camo-dialog open title="Delete item?" message="This can't be undone.">
  <camo-button slot="confirm" tone="error" text="Delete"></camo-button>
  <camo-button slot="dismiss" appearance="ghost" text="Cancel"></camo-button>
</camo-dialog>
```

```ts
const result = await showCamoDialog<boolean>({
  title: "Delete item?",
  message: "This can't be undone.",
  confirm: { text: "Delete", tone: "error", result: true },
  dismiss: { text: "Cancel", appearance: "ghost", result: false },
});
```

- The dialog is a native `<dialog>` element shown in the **top layer**; menus, popovers and tooltips use the Popover API. Focus trapping, Escape and scrim dismissal follow the overlay note. **Confirmed in W4:** one overlay frame (`CamoModal`) serves the dialog and the bottom sheet; the menu, the tooltip and the pickers use the Popover API; both forms of the dialog (declarative and `showCamoDialog`) work and attach to the nearest provider.
- The imperative helpers return a promise resolved with the result (or `undefined` when dismissed), like Flutter's `showCamoDialog<T>`. They attach to the nearest provider (or to a `host` option), so the skin and theme come from the right place.
- A declarative overlay fires `camo-close` with `detail: { result }`, and `open` is a property and attribute.
- Dismissal rules, back behavior and result types come from the base overlay note, not from this one.

#### 3.7 Lists and collections {#web-37-lists-and-collections}

- A list of items is **slotted children** (`<camo-list-item>`) when it is static, and a `state` property with a `renderItem` function when it is data-driven (`CamoPagedList` takes its paging state as an object, like the contract). Virtualization, if needed, is the component's concern and invisible to callers.
- A list of items is slotted children when static (`camo-list-item` in a `camo-list-section`) and a `state` property with a `renderItem` function when data-driven (`camo-paged-list`). **Amended in W4:** an item carries `selected` and `clickable` and reports a press as the native `click`; no container event was needed, because a controlled list sets `selected` itself. Rows and sections are drawn by the skin; the section draws the dividers.

#### 3.8 TypeScript {#web-38-typescript}

Every component exports its class, a props interface and its events, and augments the global maps so types work everywhere:

```ts
export interface CamoButtonProps {
  text: string;
  appearance?: Appearance | null;
  tone?: Tone;
  disabled?: boolean;
  loading?: boolean;
}
declare global {
  interface HTMLElementTagNameMap { "camo-button": CamoButton }
}
```

- Enums are string-literal unions (`type Appearance = "solid" | "soft" | "raised" | "outline" | "ghost" | "link"`), so attributes and properties share one type.
- Framework typings (JSX for React, `GlobalComponents` for Vue, and so on) are generated from the Custom Elements Manifest, not written by hand.
- The manifest is checked against the contract: a test fails if a component is missing a parameter, an enum value or a slot the contract names.

#### 3.9 Accessibility {#web-39-accessibility}

- The host element carries the role and label through `ElementInternals` (`internals.role`, `internals.ariaLabel`, `ariaDisabled`, `ariaBusy`), not through ids that would have to cross a shadow root. A label from `label`, from text, or from a slotted label becomes the accessible name.
- An **icon-only control** requires `label` (the contract's required label); a missing one logs in development and fails the test.
- Keyboard maps are the same as in the base notes. Focus is visible whenever it comes from the keyboard.
- `loading` sets `aria-busy` and keeps the control focusable, as in the button contract.

### 5. Edge cases {#web-5-edge-cases}

| Case | Decided behavior |
|---|---|
| Text as the default slot (`<camo-button>Save</camo-button>`) | **Open.** It is the habit of most web developers, but a renderer gets a string from an attribute and server rendering has no light DOM at render time. Proposed for later: support it only when the element can read its own text before first render, with the attribute winning if both exist. |
| A framework sets a boolean attribute to the string `"false"` | The property is the source of truth. Document that `disabled="false"` is still disabled (HTML semantics); frameworks should use the property or omit the attribute. |
| An attribute and its property are both set | The last write wins, and the attribute reflects the property. |
| A `camo-*` event name that clashes with a native one | Use the native one when its meaning matches exactly; never reuse a native name with a different meaning. |
| A component needs a parameter the contract has no name for | Add it to the base contract first (ADR), then to the three platforms. |
| Server rendering | Initial state is read from **attributes only**. Properties that hold objects must be set again on the client after hydration (the component note says which). |
| Right-to-left | `dir` comes from the document or provider; slots named `prefix` and `suffix` follow the writing direction, never left and right. |

### 6. What the spike settled (W0, srctool/camouflage-web#5) {#web-6-what-the-spike-settled-w0-srctoolcamouflage-web5}

Applied to `camo-button` and `camo-dialog`, checked by `tests/node/manifest.test.ts`, which generates the Custom Elements Manifest fresh and compares it with the contract (attributes, enum values, slots, events, inverted booleans).

| Finding | Decision |
|---|---|
| The contract's single `content: Slot` | It is the **default slot** (`<slot name="">`), not a slot named `content`. The skin's `slots.content` is `""`. Tested in the browser under both skins. |
| `title` is also a global HTML attribute | The browser would show a tooltip over the whole dialog. The element reads the attribute into the property and removes it. Other components should avoid a contract name that collides with a global attribute, or do the same. |
| Properties and decorators | `static properties` plus `declare` fields, no decorators (they need build support and are not standard everywhere). Attributes reflect only where §3.2 says. |
| Where focus goes in a dialog | The slotted actions are light DOM, so native autofocus cannot see them. The dialog focuses an `[autofocus]` child, else `dismiss`, else `confirm`, after that button's first update. The dialog frame draws no focus ring of its own. |
| Manifest tooling | `@custom-elements-manifest/analyzer` does not follow a `defineElement()` helper, so each class carries `@tagname`, `@slot`, `@fires` and `@attr` in its JSDoc. Enum values are not in the attribute's type text (only the alias name), so the check resolves aliases from `skin/types.ts`. The default slot appears in the manifest with the name `""`. |
| `click` when disabled or loading | Not fired (stopped in the capture phase); `aria-disabled` and `aria-busy` come from `ElementInternals`. Tested, axe passes. |

**Answers to the open questions**
- **Default slot as the text:** not in W0. Text stays an attribute; revisit after W1 with real usage, with the attribute winning if both exist.
- **One overlay options type or two:** two. `showCamoDialog` takes `ShowDialogOptions<T>` (actions are objects with a `result`), the declarative element takes attributes and slotted buttons. They share the field names `title` and `message`, and both close through `camo-close` with `{ result }`.

| Popover overlays | Menu, tooltip and the pickers use `popover="auto"` (or `manual`). `placePopover` puts a popup below its anchor, above when there is no room, at the anchor's start edge; CSS anchor positioning is not used. |
| Menu | An `anchor` slot and element entries (`camo-menu-item`, `camo-menu-divider`, `camo-menu-group exclusive`). The anchor announces "has popup" and expanded; arrows, Home, End and typeahead move; a click or Enter runs the item's `click` and closes; checkable items are menu item checkboxes or, in an exclusive group, radios. |
| Tooltip | Hover after a delay, keyboard focus at once; Escape, blur and press hide it; hoverable; never takes focus; the text is the anchor's description, not its name. |
| Paged list | `state = { items, loading, endReached, error }`, `renderItem`, `itemKey`; `camo-load-more` once per state near the end, `camo-retry`, `camo-refresh` (pull on touch); skeletons hidden from assistive technology, one live status. No virtualization. |
| Select | A text field plus a panel (no renderer of its own): `camo-option` children or an `options` property, `searchable`, async through `loading`, `selected-label`, `camo-open`, `camo-query` (debounced) and `camo-load-more`; a menu as wide as the field or a sheet (`auto` by window width and more than seven options). |
| Skeleton | No group element: every skeleton starts its cycle at the same moment of the page's clock. Stops under reduced motion. |
| Top bar | `scroll-offset` is a distance; `scroll-target` follows a scroller; Cupertino collapses a large title; `title-content` replaces the drawn title and the heading stays. |
| Host cannot see its children | `:host(:has(...))` is not in every engine and a server has no light DOM: slotted widgets are styled from the shadow root with `::slotted`, and a gap belongs to the widget. W1's and W2's button rule for icons was dead in Chromium and is fixed. |
| Gaps | A wheel inside a select sheet and a date wheel; context menus; submenus, popover, side sheet and command palette (W6); the structural theme fields; `refreshKeepsItems` and `itemFadeIn`. |

#### 11. What W5 settled (srctool/camouflage-web, milestone W5) {#web-11-what-w5-settled-srctoolcamouflage-web-milestone-w5}

| Finding | Decision |
|---|---|
| Progress | `camo-progress-bar` and `camo-progress-circle` take `progress` (0 to 1, clamped); none is indeterminate. A `progressbar` with a value and a percentage, or with no value while unknown. Animations are CSS; under reduced motion each becomes a slow pulse. Cupertino's unknown circle is twelve fading spokes. |
| Snackbar | A messenger, not a component: `messengerOf(el).show(message, { action, tone, duration, withDismiss })` returns a promise of `"action"` or `"dismissed"`; one messenger per provider, one message at a time in the top layer, the timer held while hovered or focused, `dismissCurrent()`, swipe to dismiss; `--camo-messenger-inset-bottom` and `-top` replace `CamoMessengerInsets`. Minimal at the bottom, Cupertino a banner at the top. Polite announcement, assertive for `error` and `warning`. |
| Banner | The tone's status icon is slot fallback (`icon` slot replaces it); `tone-info`, `tone-success`, `tone-warning` and `tone-error` registered icons change them for banner and snackbar. `status` for info and success, `alert` for warning and error. Quiet buttons in `actions` take the banner's accent through `--camo-action-color`. `dismissible` adds a ✕ and fires `camo-dismiss`. |

A 48 px touch area around the 32 px chip. |
| Badge | `count` (absent is a dot, 0 or less draws nothing, above `max` reads "99+") and `camo-badged-box` anchoring it at the top-end corner (mirrored in right-to-left); the badge is hidden from assistive technology there and its text becomes the anchor's description. |
| Avatar | `avatarInitials` and `avatarColorSeed` (FNV-1a of the UTF-8 bytes; "Dwiki Riyadi" is `0xCDC853E9`) are pure and shared with Kotlin and Dart; the photo is the app's `<img slot="image">`; initials until it loads. `camo-avatar-group` hides what is past `max` by CSS and adds a "+N" avatar once it has hydrated. |

#### 12. What W6 settled (srctool/camouflage-web, milestone W6) {#web-12-what-w6-settled-srctoolcamouflage-web-milestone-w6}

| Finding | Decision |
|---|---|
| Parts a renderer draws | A renderer is pure, so it writes `data-part` (and `data-key`, `data-id`, `data-index`) on what is pressed and the element listens once on itself (the split button's parts, pagination, the carousel's buttons, the uploader's zone and rows, the table's sort headers). |
| Popover | One pure placement function: below, then above; a side asked for (`start` and `end` follow the writing direction), then the opposite, then below; centered on the anchor and kept inside the window; it returns the physical side and where the anchor's center is, for the arrow. Click on the anchor toggles; outside click and Escape close; focus returns to the anchor; "has popup", expanded. |
| Button group and split button | Connected by default (`spaced` is the inverted `connected`); the group passes its corners to the buttons through inherited properties, so a server render is already joined. The split button is two real buttons and the real menu, opening under the whole button; `menu-only` is a menu button. |
| Side sheet and toolbar | `camo-side-sheet` docked (complementary region, scrolling content, pinned actions) and `camo-modal-side-sheet` in the overlay frame from the end edge. The toolbar's actions are `camo-icon-button`s: those that do not fit fold, in order, into a "more" menu with their labels, tones, disabled state and a checkmark for a toggle. |
| Image, rating, carousel | The image shows the browser's `<img>` in the skin's frame (placeholder, fade, error mark; no description means decorative). The rating is form-associated and adjustable (a slider; an image when read-only). The carousel is a scroll-snap strip with the strip as its one Tab stop, inert items out of sight, a page read when the scroll settles, and opt-in autoplay that stops for good once the user steps. |
| File uploader | The zone is one button firing a cancelable `camo-pick`; picked and dropped files arrive in `camo-files-dropped` and are the form value; the app sets `files` rows (progress, remove, retry, a failed row announced once). |
| Data table and tree | A real `<table role="grid">` (sticky header, `aria-sort`, selection by a `Set` or a list of keys, sorting the app's); a flat list of `treeitem`s with level, place and expanded state, lazy loading asked once. Both take object properties, which render on the server but hydrate only when set before the element upgrades. |
| Pagination, breadcrumb, steps | `pageItems` keeps a fixed length of `2 * siblings + 5`; the arrows move focus without choosing. The breadcrumb's items are data holders, the trail is drawn and folded by the breadcrumb (`planBreadcrumb`). Steps take their state from `current`; only `clickable` ones are buttons; `index` and `count` reflect for a server render. |
| Names | `connected` is the inverted `spaced`, `showIndicator` the inverted `hide-indicator`; `onClose` is `camo-close`, `onPageChange` is `camo-page-change`; `page` counts from 0; the table's `selection` is a `Set` or a list. |
| Gaps | Virtualization, content-measured and resizable columns, row expansion and cell editing; checkbox trees and range selection; a rich tooltip; the toolbar's labels, hide on scroll and vertical form; the structural theme fields (popover `showArrow`, toolbar `placement`, table `density`, tree `showLines`, and the rest of the list in the findings). |
