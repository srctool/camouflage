# Component Inventory

## 1. Why

Camouflage is a design system of its own ([Design Language](/guide/foundations/design-language)), and a skin can render it in any dialect only if Camouflage has a component for what the dialect offers. This note lists the components of the major design systems side by side, shows which Camouflage component covers each one (now or planned), and makes the gaps visible, so the roadmap is driven by real coverage instead of guesses.

:::info[Source and freshness]

The lists follow each system's published component catalog as of 2026-09: Material 3 (including the 2025 "Expressive" additions), Apple Human Interface Guidelines, Fluent 2 (web/React v9 set), and IBM Carbon. Names change between releases, so re-check the system's site when a component is picked up.

:::

### 3.3 The former v2 wave (now part of v1, ADR-21), in build order

1. `CamoListItem`, `CamoDivider`: the basis of settings screens and menus.
2. `CamoRadio` / `CamoRadioGroup`, `CamoSegmentedControl`, `CamoSlider`: the rest of the form inputs (with `CamoForm` fields).
3. `CamoSelect`, `CamoMenu`: popup menus, built on the overlay frames.
4. `CamoChip`, `CamoBadge`, `CamoAvatar`: compact, reusing Appearance and Tone.
5. `CamoProgress`, `CamoSnackbar`, `CamoBanner`, `CamoTooltip`: feedback.
6. `CamoTabs`, `CamoNavigationBar`, `CamoNavigationRail`, `CamoNavigationDrawer`: app navigation chrome (not routing).
7. `CamoFab`, `CamoSearchField`.

Each new component reuses the vocabulary (`appearance`, `tone`, levels), gets a renderer in the skin contract, a component theme, and a row in each skin's alignment table.

## 4. Build steps

1. Keep this note updated whenever a component is added or a design system publishes new ones (with an "as of" date).
2. Before promoting a Later component, re-check each system's catalog (they publish new components often).
3. For every new component: check it against ADR-23 (every skin can draw a reasonable equivalent, and every parameter works in every dialect; use the four system columns above), then base contract note → Kotlin note → Flutter note → skin renderer → alignment table row, the same flow as v1.

## 5. Edge cases

| Case | Decided behavior |
|---|---|
| A component exists in only one system (e.g. Apple's activity rings) | Out of scope, unless two real projects need it. |
| Two systems' components overlap differently (Apple's pickers cover Material's select, date picker and time picker) | Camouflage keeps separate components (`CamoSelect`, `CamoDatePicker`). A Cupertino skin may render several of them with native wheel pickers. |
| Navigation chrome vs routing | Navigation *components* (tabs, bars, rails, drawers) are in scope. *Routing* stays out of core (ADR-19). |
| Charts, data visualization | Out of scope for Camouflage. It would be a separate family package if ever needed. |
