# Camouflage — Overview

## Concept {#concept}

:::note[One sentence]

Camouflage is a component library where **what a component is** stays fixed and **how it looks** comes from a swappable **Skin** plus a **Theme**. A new app gets a new Theme, not new components.

:::

### The problem

Every new app starts with a Figma file that has its own design system. The usual answer is to rebuild the same components again: `PrimaryButton`, `AppTextField`, `BrandCard`. Each time the logic (state, focus, accessibility, callbacks) is written again, even though only the *look* changed.

Existing toolkits make this worse in different ways:
- **Flutter** ships Material *and* Cupertino, but they are two separate widget sets (`ElevatedButton` vs `CupertinoButton`). Switching means changing call sites.
- **Jetpack Compose** lets you build a custom design system on `compose.foundation` with your own `CompositionLocal`s. But `material3` components read only `MaterialTheme`, there is no built-in Cupertino, and there is no "skin switch". A custom look usually means rewriting the component.

Camouflage separates the three concerns, so the component is written **once**.

### The three concepts

| Concept | Owns | Changes when… | Example |
|---|---|---|---|
| **Theme** | Token *values*: color, typography, shape, spacing, elevation, motion, plus optional **component themes** (button height, text-field shape…) | the brand changes (a new client, dark mode) | `brandLightTheme`, `brandDarkTheme` |
| **Skin** | *Structure and behavior*: how each component is built, press feedback, surface treatment, and **default component proportions** | the design language changes (Material → Cupertino → Liquid Glass) | `MaterialSkin` |
| **Component** | The public API apps call: text values, icon widgets, callbacks, appearance and tone. It draws nothing. | almost never | `CamoButton`, `CamoTextField` |

:::tip[Rule of thumb]

If a designer changes a **value** (a color, a radius, a button's height), that is a Theme: a global token, or a component theme. If they change **how a thing is built or behaves** (a dialog becomes a bottom alert, ripple becomes an opacity fade), that is a Skin.

:::

### Glossary

| Term | Meaning |
|---|---|
| **Token** | A named design value (`colors.primary`, `spacing.l`). |
| **Role** | A semantic token name that says *what it's for* (`onSurface`), not *what it is* (`grey900`). |
| **Renderer** | The part of a Skin that draws one component: `ButtonRenderer`, `DialogRenderer`. |
| **State** | The data a renderer needs to draw a component: `enabled`, `pressed`, `checked`, `error`. |
| **Slot** | A place where the caller passes a widget: an icon (`prefixIcon`), a nested component (a dialog's `confirm` button) or layout content (a card's `content`). Text is never a slot; it's a value. |
| **Component theme** | Per-component values (`ButtonTheme(height = 48, shape = 12, iconSize = 20)`), like Flutter's `FilledButtonThemeData`. Set in the theme, merged over the skin's defaults. |
| **Icon style** | The size and color a component sets around its icon widgets, so `AppIcon.save()` needs no parameters inside a button. |
| **Tone** | The color family of a component: `Default`, `Error` (destructive), `Success`, `Warning`, `Info`. It's independent of the appearance. |
| **Surface level** | How separated a region is from the background: `Surface`, `Lowest` … `Highest`. |
| **Appearance** | A component's visual weight, in Camouflage's own words: `Solid`, `Soft`, `Raised`, `Outline`, `Ghost`, `Link`. Skins render it in their dialect (Material's Filled, Apple's `.borderedProminent`, …). See [Design Language](/guide/foundations/design-language). |
| **Surface treatment** | The "material" of a skin: paper (opaque plus shadow), glass (refracting blur), acrylic (frosted). |
| **Interaction feedback** | How a skin shows a press: ripple, opacity fade, scale. |
| **Provider** | `CamouflageProvider`, which puts a Skin and a Theme into the UI tree for everything below it. |

3. **Each note zooms in the same way:**

   4. **Build steps**: a checklist ending in *Done when*. This is also the episode script.

### How platform notes inherit

- `base/` API is **pseudocode** (Kotlin-like). It fixes names, parameters and meaning.
- A platform note **keeps every base name** and adds only platform details: `Modifier`, `BuildContext`, `@Composable`, `const`, and so on.
- If a platform can't follow the base contract, the platform note says so in §5 Edge cases and links the decision in [Decisions](/guide/project/decisions).

### Kotlin-wide conventions for Camouflage {#kotlin-kotlin-wide-conventions-for-camouflage}

1. **`explicitApi()`** in both libraries: every public declaration says `public`. That keeps the API surface deliberate, and the ABI dump readable.
2. **`@Immutable` / `@Stable`** on every theme, style, state and skin class, so Compose can skip recomposition. Theme classes are `data class`es with only `val`s.
3. **`modifier: Modifier = Modifier`** is the first optional parameter of every public composable (Compose API guidelines), a platform extra on top of the base contract.
4. **Icon and content parameters are `@Composable () -> Unit` lambdas.** That's how Compose passes widgets (base ADR-12).
5. **No Material dependency in v1.** Core and the Minimal skin use only `foundation` + `ui` (the Minimal skin draws its own fade feedback). A Later Material skin adds `material-ripple` for its ripple node, and never `material3`.
6. **Common code only.** `expect`/`actual` is limited to the platform table in [Architecture](/guide/architecture/architecture) §2.4.
7. **No DI, no networking, no ViewModels in the libraries.** Those belong to apps. (Your Koin/Ktor/ViewModel conventions apply to the `sample` app, if it grows.)

### Dart-wide conventions for Camouflage {#dart-dart-wide-conventions-for-camouflage}

1. **`widgets.dart` only in core.** Lint it: a custom `analysis_options` rule, or a CI grep, fails on `package:flutter/material.dart` / `cupertino.dart` / `material_ui` imports under `camouflage_core`.
2. **`Camo` prefix on theme and style classes.** Flutter's `widgets` library already has `IconTheme`, and apps importing `material_ui` get `ButtonTheme`, `CardTheme`, `DialogTheme`… Camouflage's are `CamoButtonTheme`, `CamoButtonStyle`, `CamoIconTheme`, and so on. (Kotlin has no such clash; see [Theme](/guide/foundations/theme#implementation).)
3. **Immutable data with `copyWith` and `lerp`**, written by hand (no `freezed` in a published library, to keep consumers' codegen out of it). `@immutable` on every theme, style and state class, with `==`/`hashCode` via a small `Equatable`-style mixin or by hand.
4. **Enums are `lowerCamelCase`**: `Appearance.solid`, `Tone.error`, `SurfaceLevel.highest`. The same names as the base, in Dart style.
5. **Stateless public widgets where possible.** Interaction and text-editing state lives in `State` objects inside core, never in the app's widgets.
6. **Library state uses Flutter primitives only** (`ChangeNotifier`, `ValueListenable`, `InheritedWidget`). Your Riverpod/GetIt conventions apply to the `example` app, not the library.
7. **Files ≤ 1000 lines, one public widget per file, `snake_case` file names matching the class** (your Flutter conventions).
