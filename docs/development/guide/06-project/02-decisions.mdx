# Decisions

## 1. Why

Short architecture decision records (ADRs), so that later you (or a viewer, or an AI agent) can see **why** Camouflage is shaped the way it is, and what it would cost to change. Add a new ADR whenever a base contract changes.

## 2. Shape

Each ADR has three parts: **Context → Decision → Consequences**. The status is Accepted unless marked otherwise. Numbers are never reused, and superseded ADRs stay, marked "Superseded by ADR-N".

## 3. API

### ADR-1 Skin and Theme are separate layers
- **Context:** a single "theme" can't express both "the brand is purple" and "dialogs are iOS alerts". Making everything a theme gives fake Cupertino; making everything a skin brings back per-project components.
- **Decision:** Theme = token values only. Skin = structure, behavior and surface.
- **Consequences:** a new brand is a theme only. A new design language is a skin. Two concepts to learn instead of one.

### ADR-2 Core components delegate rendering to the active skin
- **Context:** apps must be able to switch design language without changing call sites.
- **Decision:** apps call core `Camo*` components, which call `skin.x.render(state, slots, theme)`. The skin is resolved from the tree.
- **Consequences:** one-line skin switching, nested skins, adaptive roots. Core must define a complete contract for every component before a skin can draw it.

### ADR-3 Skins ship as separate libraries
- **Context:** apps shouldn't pay for skins they don't use, and skins should version on their own.
- **Decision:** `camouflage-core` plus one module per skin. Skins use only core's public API.
- **Consequences:** proves the contract is enough for third-party or AI-built skins. More modules to publish.

### ADR-4 Semantic variants in core (amended by ADR-11)
- **Context:** `filled`/`tonal` are Material words, and a Cupertino skin has no "tonal".
- **Decision:** core uses design-language-neutral variants and roles (`SurfaceLevel`, `ElevationLevel`, `Tone`, and the variant enums from ADR-11). Skins map them.
- **Consequences:** a neutral API. Designs needing a fourth variant use a renderer override or a custom token set (see [CamoButton](/components/actions/camo-button) §5).

### ADR-5 Kotlin first, then Flutter, per milestone
- **Context:** Android is the author's main platform, and a mirrored series makes good content.
- **Decision:** each milestone is built in Kotlin (Compose Multiplatform), then ported to Flutter.
- **Consequences:** Flutter may reveal contract issues late. Fix the base note first.

### ADR-6 Figma integration via the Figma MCP + an agent, not a custom generator
- **Context:** Figma's MCP server already exposes variables, design context and Code Connect to AI agents.
- **Decision:** Camouflage provides a naming contract, precise contracts, an agent guide and Code Connect mappings. There's no bespoke codegen tool.
- **Consequences:** less tooling to maintain. The results depend on agent quality and on the Figma file following the conventions.

### ADR-7 Material is the only skin in v1 (superseded by ADR-22)
- **Context:** Material is the author's daily design system. Liquid Glass needs hard rendering work (backdrop blur and refraction).
- **Decision:** v1 ships `MaterialSkin`. Cupertino, Liquid Glass and Fluent come Later, each as its own module.
- **Consequences:** the Skin abstraction is proven by `DebugSkin` + `MaterialSkin` only. A second real skin may still find gaps in the contract.

### ADR-8 Components are controlled
- **Context:** runtime skin and theme switches must not lose user data, and apps need to filter or confirm changes.
- **Decision:** components hold no source of truth. Values in, callbacks out. Only visual interaction state is internal.
- **Consequences:** a little more code at call sites. Skin switches are safe, and validation, confirmation and async toggles need no special API.

### ADR-9 No default skin or theme in core; fail fast
- **Context:** a silent default hides a missing provider until someone notices the wrong look.
- **Decision:** a missing provider throws a clear error naming the component and what is missing. Starter themes ship from skin modules.
- **Consequences:** a one-time setup line for every app. Core stays visually neutral.

### ADR-10 The editable text node lives in core, not in the renderer
- **Context:** if a renderer created the text input, a skin switch would recreate it, losing focus, cursor and keyboard.
- **Decision:** `CamoTextField` owns the platform editable node and passes it to the renderer as the `input` slot to place.
- **Consequences:** skins can't replace the input engine itself. Focus survives skin switches.

### ADR-11 Variants use designer vocabulary
- **Context:** `Emphasis { High, Medium, Low }` (ADR-4's first naming) is Material's internal term. Developers and designers say "primary button" or "outlined card", and Figma component variants use those words.
- **Decision:** buttons and icon buttons take `variant: ButtonVariant { Primary, Secondary, Tertiary }`. Cards take `variant: CardVariant { Filled, Elevated, Outlined }`, because "primary card" isn't common language, and filled, raised and bordered boxes exist in every design language.
- **Consequences:** Figma `variant=primary` maps directly to code, which helps Code Connect ([Figma and AI](/guide/integrations/figma-and-ai)). `ButtonVariant.Primary` and `colors.primary` share a word; in Material they line up (a Primary button is filled with `primary`), and other skins document their mapping.

### ADR-12 Text is a value, icons are widgets, layout is a slot
- **Context:** the first contract used slots everywhere (`CamoButton(onClick) { CamoText("Save") }`), Compose style. The author's working style (Flutter and Android) is: text as a value, icons as app-level icon widgets that pick up size and color from the component's icon theme, and prefix/suffix icons as in design files.
- **Decision:** labels, titles and messages are `String` values drawn by the renderer. Icons are passed as widgets (`prefixIcon`, `suffixIcon`, `icon`), and every renderer sets an ambient `IconStyle(size, color)` around them. Nested actions are Camouflage components. Only free layout (`CamoSurface`, `CamoCard`, `CamoDialog.content`) is a slot. `CamoCheckbox` and `CamoSwitch` take an optional `label` and build the whole row.
- **Consequences:** one obvious way to call each component, matching Figma properties (text layer → `text`, prefix icon → `prefixIcon`), which is good for Code Connect and AI agents. Custom content inside a button or title (badges, logos) needs a renderer override or an app widget. In Compose, icon parameters are small `@Composable` lambdas, because that's how Compose passes widgets.

### ADR-13 A 42-role color model with status tones
- **Context:** the first 20 roles followed Material 3 closely. Comparing Apple HIG, Fluent 2 and IBM Carbon showed that every other system has **status colors** (success, warning, info), several **surface levels**, and **inverse** colors. Material has only `error`. Camouflage must be able to carry other design systems.
- **Decision:** `CamoColors` has 42 roles in 7 groups: brand (primary, secondary, tertiary × 4), surfaces (6 levels), content (2), lines (2), status (error, success, warning, info × 4), inverse (3), scrim. A `Tone { Default, Error, Success, Warning, Info }` parameter on buttons, icon buttons and cards picks the color family, independently of the variant. Destructive = `tone = Error`. `CamoColors.fromSeed` generates all roles from a few seeds with the Material tonal-palette algorithm.
- **Consequences:** a mapping table from each major design system onto Camouflage roles ([Theme](/guide/foundations/theme) §3.3) makes future skins and Figma imports mechanical. More roles for Figma files to define, offset by `fromSeed`. `CamoSurface` uses `level: SurfaceLevel` (no clash with `Tone`).

### ADR-14 Text styles and colors are passed as values; rich text through spans
- **Context:** the author defines complete text styles (weight included) as constants and adjusts them with `copy`. Real screens need links and bold words inside sentences (consent checkboxes, terms).
- **Decision:** `CamoText(style: CamoTextStyle, color: Color?)` takes values (`typography.titleMedium.copy(fontWeight = Bold)`, `Camouflage.colors.success`), not role enums. `CamoText.rich(spans)` with `CamoSpan(text, fontWeight?, italic?, color?, underline?, link?)` maps to Flutter `TextSpan` / Compose `AnnotatedString`. Checkbox and switch accept `labelSpans`.
- **Consequences:** full flexibility for callers. A skin can't restyle a caller's text by role (it can still style links and component-owned text). Links are real accessible links on both platforms.

### ADR-15 Component themes: theme overrides merged over skin defaults
- **Context:** changing a button's height or radius, the most common Figma request, required a full renderer override. Flutter solves it with per-component theme data (`FilledButtonThemeData`), and the author uses that pattern, including the button configuring its icon theme.
- **Decision:** `CamoTheme.components` holds optional per-component themes (`ButtonTheme`, `TextFieldTheme`…) whose fields are all nullable. Each renderer declares `defaults(theme)`, a complete component theme that may reference global tokens. Core resolves `style = defaults(theme).merge(theme.components.x)` and passes it to `render`. Renderers take every adjustable size and color from `style`.
- **Consequences:** most Figma designs need only a theme (global tokens + component overrides), with no code. Brand themes stay portable across skins, because unset fields use each skin's own defaults. Renderer overrides are only for structural differences. Each component gains a theme class with a `merge`. A test per renderer guards against literals.

### ADR-16 Text field keeps `value: String`; filtering and formatting live in core
- **Context:** with a plain `String`, formatting inside `onValueChange` makes the cursor jump to the end. A cursor-aware value type (`TextFieldValue`, `TextEditingController`) fixes that, but pushes selection handling onto every call site and differs a lot between platforms.
- **Decision:** keep `value: String`. Add `inputFilter: CamoInputFilter?` and `displayFormat: CamoDisplayFormat?`, applied by core (which owns the editable node, ADR-10) through each platform's cursor-safe mechanism (Compose `InputTransformation`/`OutputTransformation`, Flutter `TextInputFormatter`). `value` is always the raw text.
- **Consequences:** simple call sites, no cursor jumps, and raw values ready for validation and APIs. The app can't set the cursor programmatically in v1; a state-based overload can add that later without breaking the API.

### ADR-17 Forms: Flutter's Form/FormField model on both platforms, rules as objects
- **Context:** apps rewrite form validation every time. The author likes Flutter's `Form` + `FormField` + `AutovalidateMode`, and already uses validator *objects* (constants or classes) in Flutter and Android. Compose has no Form equivalent. Building UI and rules from JSON is a separate product, Camouflage Blueprint.
- **Decision:** core ships `CamoForm`, `CamoFormState`, `CamoFormField<T>`, and `CamoTextFormField` / `CamoCheckboxFormField` / `CamoSwitchFormField`, with Flutter semantics (fields register with the nearest form; `validate`, `save`, `reset`; `ValidateMode` = `AutovalidateMode`, default `Disabled`; `forceError`). Checks are `CamoRule<T>` objects (`fun interface`) plus `CamoRules` built-ins. There's **no JSON or registry in core**; that's Blueprint's job. Form fields hold their own value, a deliberate exception to ADR-8, as in Flutter.
- **Consequences:** Flutter-familiar forms in Compose. Unlike Flutter, the **form owns field state by key**, so forms work in lazy lists (off-screen fields keep values, validate and save; `revealField` scrolls to the first invalid one). Form fields inside a form need a `key`. Plain controlled components remain for apps that manage state themselves. `CamoTextField` gains `onFocusChanged`, and the toggles gain `error`. Async checks stay app-side (`setErrors`) in v1.

### ADR-18 Every platform from M0; live docs deferred
- **Context:** Camouflage already targets iOS, so its Kotlin code has to be common-only anyway. Compiling for desktop and web as well costs little: Gradle targets, CI jobs, and dependency checks. The author also wants to explore KMP fully. Live component previews in the Docusaurus docs site (`srctool/camouflage`) are real extra work, and Compose web was Beta when this was decided (2026-09).
- **Decision:** from M0, core and skins compile for **Android, iOS, desktop (JVM) and web (`wasmJs`)** on Kotlin, and for all six Flutter platforms. The sample app runs on each. **Live docs (a gallery app + `<LivePreview>` iframes in Docusaurus) are deferred** until Compose web is stable.
- **Consequences:**
  - Dependencies must support all four Kotlin targets.
  - CI runs one build per platform (iOS needs a macOS runner).
  - Web and desktop need a few `actual`s (see [Architecture](/guide/architecture/architecture) §2.4).
  - Desktop exercises hover, focus rings and keyboard traversal for real.
  - If a web-only (Beta) problem blocks a release, the web job can be skipped for that release without touching other code.
  - Accessibility testing stays on Android and iOS, because web renders to a canvas.

### ADR-19 Overlays open through each platform's navigator, the way Material does
- **Context:** the author wants dialogs and sheets written like small pages in their own files (own state, own ViewModel/notifier, typed result), with no dialog flags in screens. Camouflage is a peer of `material_ui`/`cupertino_ui` (Flutter) and material3 (Compose), and Material doesn't bring its own overlay system: it plugs into the platform's navigator. Navigation 3 (stable, multiplatform via JetBrains) supports dialog and sheet entries through scene strategies, with a per-entry ViewModel scope.
- **Decision:**
  - **Flutter**: `showCamoDialog` / `showCamoBottomSheet` push Camouflage routes and return `Future<T?>`, exactly like `material_ui`.
  - **Compose**: dialogs and sheets are **registered Navigation 3 entries** with Camouflage scene metadata, rendered by `CamoDialogSceneStrategy` / `CamoBottomSheetSceneStrategy` from the official **`camouflage-navigation3`** artifact. Results go through `CamoNavResults`.
  - Core provides the **frames** (usable standalone, like Material's `ModalBottomSheet`) and the **content components** (`CamoDialog`, `CamoBottomSheet`, which joins v1).
  - Core contains no router.
- **Consequences:**
  - The same content and look on both platforms, with a platform-idiomatic way to open them.
  - Compose sheets are deep-linkable and restorable (process death); Flutter's aren't by default (as in Material).
  - `CamoDialog` loses its `onDismissRequest` parameter (dismissal goes through the frame).
  - An earlier draft with a custom Compose `show` host was dropped in favor of this.
  - Review follow-ups: Compose gets `showForResult` (suspend) on top of `CamoNavResults`. Flutter also gets `CamoSheetPage`/`CamoDialogPage`, so overlays can be GoRouter routes without modifying GoRouter. Overlays are non-opaque: the page behind stays visible under the scrim. `widePresentation` and `stackedScrim` are design-team options in the component themes.

### ADR-20 Camouflage is its own design system; one Appearance scale replaces per-component variants
- **Context:** `ButtonVariant { Primary, Secondary, Tertiary }` (ADR-11) named *rank*, and couldn't express the styles designers actually use (filled, tonal, elevated, outlined, text, link). Rank names also mean different things across systems (Carbon's "tertiary" is outlined, Polaris's is text-like). `CardVariant` used Material's style words. The author wants Camouflage to be a design system of its own, whose language adapts to other systems through skins.
- **Decision:** Camouflage has its own design language ([Design Language](/guide/foundations/design-language)): principles, foundations, vocabulary, components and an interaction model. Skins are **dialects** that must publish an alignment table. Components with visual variants take **`appearance: Appearance { Solid, Soft, Raised, Outline, Ghost, Link }`** plus **`tone`**, with per-component subsets and core fallbacks. `ButtonVariant` and `CardVariant` are removed. This supersedes the naming part of ADR-11.
- **Consequences:**
  - One vocabulary across code, Figma (`appearance=…`) and docs. It's future-proof for chips, badges and tags.
  - Material maps directly (Filled, Tonal, Elevated, Outlined, Text); Link and Solid cards are Camouflage additions.
  - Other dialects map by table, with documented fallbacks.

### ADR-21 The full component set is v1; the project follows a waterfall lifecycle
- **Context:** the component inventory ([Component Inventory](/guide/foundations/component-inventory)) showed that the original 15 components cover only the core of each design system. The author prefers to include the next wave in v1, and works waterfall-style: the complete design documentation first, then implementation.
- **Decision:** v1 = 34 component notes (15 original + 20 former-v2, with `CamoSelect` reusing other renderers). The lifecycle has four phases:
  1. **Design**: all base contracts, reviewed.
  2. **Platform design**: all Kotlin notes, then all Flutter notes, each reviewed.
  3. **Implementation**: in milestone order M0–M8, Kotlin then Flutter.
  4. **Verification + release**: M9 (testing, publishing v0.1).
- **Consequences:**
  - The skin contract has 33 renderers (35 after ADR-29, 39 after ADR-35), so a new skin is a bigger job (the checklist and `DebugSkin` still apply).
  - v0.1 ships later but covers 75–85% of each major design system.
  - Milestones remain the build and episode order, not separate releases.

### ADR-22 Camouflage's own Minimal skin is the v1 skin; other dialects are documented for Later
- **Context:** copying an existing design system's skin (Material, Apple, Fluent, Carbon) means matching hundreds of exact external measurements and behaviors. The author wants Camouflage to have its own look, following a minimalism concept, and to build that first.
- **Decision:**
  - v1 ships **`MinimalSkin`** (module `camouflage-skin-minimal`): flat surfaces (no shadows), hairline borders, monochrome ink by default with one optional accent, opacity feedback, and system fonts ([Minimal Skin](/guide/skins/minimal-skin)).
  - **Material, Cupertino (with Liquid Glass as a surface option), Fluent and Carbon** are fully documented as Later skins. Shipping any of them is a separate decision.
  - `CamoColors.fromSeed` gains a `neutral` seed.
  - Supersedes ADR-7.
- **Consequences:**
  - The v1 skin needs no Material dependency on either platform (`material3`, `material-ripple`, `material_ui` aren't needed in v1).
  - The component notes keep a "Material mapping preview" as a reference dialect. The v1 values live in the Minimal skin's defaults table.
  - The four other skin notes prove the contract against very different anatomies (Apple alerts and wheel pickers, Carbon bottom-border fields) before implementation.

### ADR-23 Core contracts are the common ground of every dialect
- **Context:** documenting five skins showed where dialects differ: Apple stacks alert buttons, Carbon puts dialog actions in a full-width row, only Material has a hero icon in dialogs. If core took on each dialect's extras, it would stop being neutral, and every new skin would need to handle features it doesn't have.
- **Decision:**
  - A component parameter belongs in core only if **every documented dialect** (Minimal, Material, Cupertino, Fluent, Carbon) can render it meaningfully.
  - Dialect-only features stay out of core. The developer composes them in a slot (e.g. dialog `content`), or the skin exposes them as a skin option or component-theme field.
  - The component owns semantics, input, dismissal, focus and results. The renderer owns the look and the **arrangement** of the slots it receives. Contracts pass separate slots (e.g. `confirm`, `dismiss`) rather than one opaque row whenever a dialect needs to arrange them.
- **Consequences:**
  - Adding a parameter means checking the component's row in every skin note.
  - `CamoDialog` gets no `icon` parameter (Material only).
  - The first audit of all 33 contracts (2026-09-27) changed:
    - `CamoSegmentedControl`: the multi-select overload is removed (iOS and Carbon are single-select); multi-select uses filter chips.
    - `CamoFab.size` → `FabTheme.size`; `CamoBottomSheet.showHandle` → `BottomSheetTheme.showHandle`; `CamoNavigationRail.alignment` → `NavigationRailTheme.alignment`; `showLabels` → `NavigationBarTheme` / `NavigationRailTheme`.
    - `CamoTopBar.scrolled: Boolean` → `scrollOffset: Dp`, so collapsing dialects work.
    - Wording: `CamoTabs` Solid/Ghost mean prominent/quiet; `CamoListSection.level` sets the fill only.
    - Cupertino fallbacks documented: scrollable tabs, horizontal radio groups.
  - Components pass the same test: a component stays in core if every skin can draw a reasonable equivalent (e.g. `CamoFab` as a plain floating button).
  - Skin notes stay the edge-case reference, even for skins that never ship.

### ADR-24 Core token defaults are Camouflage's own values
- **Context:** core's default shapes, motion and `fromSeed` neutrals were Material's numbers, so a theme built only from core looked like Material. Camouflage is its own design system (ADR-20) and Minimal is its dialect (ADR-22).
- **Decision:**
  - Core defaults take the Minimal values: gray neutrals in `fromSeed` (`neutral = null` → zero chroma), Camouflage's neutral tone table, radii 4/6/8/12/16, motion 120/200/300 ms, and `CamoTypography.system()` (system font, weights 600/500/400).
  - Core copies the numbers. It never depends on the skin module.
  - `CamoSpacing` gains `none = 0`. The default status seeds stay.
- **Consequences:**
  - A theme with only a brand color looks like Camouflage. `minimalTheme()` mostly adds the ink primary.
  - Later dialects bring their own numbers (e.g. the Material skin's `materialColors(seed)` with tinted neutrals and M3 shapes and motion).
  - The Kotlin neutral tones are snapshot-pinned, not compared with MaterialKolor's scheme output.

### ADR-25 Overlay dismissal and drag reach the renderer
- **Context:** the Architecture review (2026-09-27). Carbon and Fluent draw a ✕ on dialogs and Cupertino sheets can show "Done", but only when the overlay may be dismissed. The slider kept its own `dragging` flag, and the switch thumb couldn't be dragged.
- **Decision:**
  - `DialogState` and `BottomSheetState` carry `dismissible` and `onDismissRequest`, supplied by the overlay frame. A close affordance calls `onDismissRequest`, which takes the same path as back/Esc, so vetoes still apply.
  - `InteractionState` gains `dragged`. `SliderState.dragging` is removed in favor of it, and the switch thumb is draggable in v1.
  - `Camouflage.skinOrNull` / `themeOrNull` (Flutter: `maybeSkinOf` / `maybeThemeOf`) let optional libraries detect a provider. `Camo*` components never use them.
- **Consequences:** skins without a close affordance ignore the new fields. Every interactive component reports `dragged = false` unless it supports dragging.

### ADR-26 The camouflage repo hosts the family packages
- **Context:** the family grew (Blueprint, Storybook, a generator, page templates like a camera page). Separate repos each need their own build, CI and version pinning against core.
- **Decision:**
  - A package that depends on Camouflage, or generates code for it, lives in the camouflage repo as its own package (a Gradle module in `camouflage-kotlin`, a pub package in `camouflage-dart`): Blueprint, Storybook, `camouflage-filesystem` (its browser/picker UI is built with Camouflage, like Storybook), `camouflage-generator`, templates (one package each, e.g. `camouflage-camera`).
  - A package that works without Camouflage would live in its own repo (none today; srctool gradle-conventions after extraction).
  - Core, skins and `camouflage-navigation3` are versioned together. The other packages are versioned and released independently (Melos independent versioning; per-module versions in Gradle), and the Kotlin BOM pins them at tested versions (ADR-27).
  - Docs stay per package in the vault (`projects/camouflage-*`).
- **Consequences:** family packages build against the current core, with no composite build. CI builds only the packages a change touches. Core never depends on a family package (Roadmap dependency rules).

### ADR-27 Dependency layers, and safe use of several packages
- **Context:** with the family in one repo, a convenient import (a skin shipping stories, camera saving through filesystem, a core uploader using filesystem, a generator depending on core) could create a cycle. Apps that combine several packages risk version skew.
- **Decision:**
  - Layers 0 (core) → 1 (skins, navigation3) → 2 (family packages and templates) → 3 (glue modules, samples, apps). Dependencies only go to lower layers, never within a layer. Build tools (generator, build-logic) depend on nothing from Camouflage.
  - Same-layer packages cooperate through callbacks or slots, connected by the app or a layer-3 glue module. Core components that need a family feature take callbacks (`CamoFileUploader(onPick)`).
  - The Kotlin BOM pins every package at versions tested together. Dart family packages use caret ranges on core and are re-released by CI when core's minor version bumps.
  - A CI check enforces the layers on both platforms, including Dart `dev_dependencies`.
- **Consequences:** no cycles by construction. Apps import the BOM (Kotlin) or let pub resolve (Dart). Family packages carry a "works with core" table.

### ADR-28 Brand designs are expressed through themes first
- **Context:** in practice, a product's designers make their **own** design system, benchmarked against others but not following any of them. The author's usual path was to take Material and rebuild each component to match the Figma design. Camouflage exists to replace that: the common case is **one brand design on top of the Minimal skin**, not switching between Material and Cupertino.
- **Decision:**
  - The customization ladder, cheapest first: (1) theme tokens → (2) component-theme fields → (3) a renderer override (`MinimalSkin.copy(button = …)`), either written by the app or **borrowed from another skin** (`MinimalSkin.copy(tabs = CupertinoSkin.tabs)`) → (4) a new skin. A typical brand needs 1 and 2; product feedback like "make the tabs behave like Apple's" is answered with 3.
  - Skins are therefore also **libraries of renderers**: each one exposes its renderers individually, and a borrowed renderer keeps its structure and behavior while using the app's theme and the host skin's surface treatment and feedback (Skin Contract §3.5).
  - Any layout or proportion choice a brand design commonly changes is a **component-theme field** with a per-skin default, not a hard-coded renderer decision and not a per-call parameter. Examples: `TextFieldTheme.labelPlacement`, `CheckboxTheme.labelPosition`, `SwitchTheme.labelPosition`, `RadioTheme.labelPosition`, `NavigationBarTheme.showLabels`, `FabTheme.size`, `BottomSheetTheme.showHandle`.
  - Components with an `appearance` take `Appearance? = null`; `null` resolves to `XTheme.defaultAppearance`, then the skin's default (Button, IconButton, Fab, Card, Chip, Badge, Banner, Tabs).
  - Every component review asks: "would a brand's Figma change this?" If yes, it becomes a theme field.
- **Consequences:** more component-theme fields, all optional. The Minimal skin's renderers read them instead of constants (already required by the "no literals" rule). ADR-23 still decides what goes into the component API; ADR-28 decides what goes into its theme.

### ADR-29 CamoPagedList and CamoSkeleton join v1; the data side is Sinew
- **Context:** every app rebuilds an API-backed list (refresh, next page, skeletons, empty and error states). The author's own list container worked like a framework: it spanned data → domain → presentation through generic response models and a state-management type.
- **Decision:**
  - Split at a plain state object. Camouflage core gets `CamoPagedListState<T>` (items, `PagedLoad` None/Initial/Refresh/More, `endReached`, `PagedError` with a FirstPage/NextPage scope) and **`CamoPagedList`**, a controlled component with `onLoadMore`, `onRefresh`, `onRetry`. It never fetches.
  - **`CamoSkeleton`** moves from Later to v1 (the loading rows).
  - `CamoAsyncSelect` takes the same state and callbacks instead of a `loadOptions` function (a delegate pattern: the app drives it).
  - The data side (generic `Response`/`PagingResponse` mapping, paging use cases, `Result`, view state) is **Sinew**, a sibling project (Overview). Neither depends on the other; an optional glue package adapts Sinew's state.
- **Consequences:** v1 = 36 component notes and 39 renderers. Refresh and load-more are distinct `PagedLoad` values. Sinew's `PagingState` carries an explicit `loadType` (its `Pager<T>` owns the paging convention), so its adapter is a direct mapping.

### ADR-30 Room for imaginative designs: options, behavior inputs, building blocks
- **Context:** product designs go beyond any design system: a bottom navigation that is pinned, floating or hides on scroll, or one that drags up into a sheet with a menu. The same happens to other components (tabs, text fields, top bars). A fixed component API can't anticipate every idea, and a renderer override is too heavy for a one-screen idea.
- **Decision:** each complex component offers four levels, cheapest first:
  1. **Theme options** for variants that recur across products (`NavigationBarTheme.placement: Pinned | Floating`, indicator styles, title alignment).
  2. **Behavior inputs** that stay controlled: the component reacts to a value (`visible`, `scrollOffset`) and a platform helper computes it (`rememberHideOnScroll`), instead of hidden built-in scroll magic.
  3. **Building blocks:** the component's skin-styled, accessible parts are public (`CamoNavBarContainer`, `CamoNavItemButton`), so an app can build a one-off design that still looks and behaves like the rest of the app.
  4. A **renderer override**, or the app's own component.
- **Consequences:** component notes get a "building blocks" part where designs commonly go their own way. Every review asks: "what do designs imagine for this component, and which level covers it?"

### ADR-31 Tooling works without Figma, around one tokens format
- **Context:** the Figma MCP needs a paid Figma seat, and Figma's variables REST API is limited to its top plan. Many designers and teams have neither, and some use Penpot, Tokens Studio or no design tool at all.
- **Decision:**
  - One interchange format: **Camouflage tokens JSON** (W3C Design Tokens + the naming contract), covering theme tokens **and component themes** (sizes, role references, layout choices as strings and Booleans).
  - `camouflage-contract.json`, generated from core's code, describes every component and component-theme field; the tools validate against it, so they never drift.
  - Tools, in order: the `camo` command in `camouflage-generator` (import, validate, export, lint), `camouflage-mcp` (Camouflage's own MCP server, including screenshot-to-theme), a free-plan Figma plugin, Camouflage Studio.
  - All are build tools (ADR-27): they depend on nothing from Camouflage's runtime.
- **Consequences:** the Figma MCP becomes one optional source among several. Brand themes can round-trip between code and tokens files. Studio previews each target with its real renderer (one canvas per platform), and the generator's targets can grow (web, once a web port exists).

### ADR-32 Brand vocabularies are typed token sets, generated by Camouflage's codegen
- **Context:** brands name tokens their own way (Tailwind scales, Mantine indexed shades, named sizes). On the web those can be CSS variables used anywhere; in Kotlin and Dart they must be typed and mapped to Camouflage. Flutter's `ThemeExtension` needs hand-written `copyWith`/`lerp` and can't be referenced by theme roles. The untyped `extensions` map was weaker still.
- **Decision:**
  - `CamoTheme.extensions` is replaced by `tokenSets: List<CamoTokenSet<*>>`: typed classes, read with `Camouflage.tokens<T>()`, scoped by providers and blended by animated theme switches. `CamoColorScale` / `CamoDimensionScale` keep numeric names (`brand[600]`).
  - The intended path is **codegen**: the tokens JSON's `custom` groups (and `skin` section) → the `camo` generator writes the token-set classes, the themes (roles referencing brand tokens), the component themes and the skin (a base skin plus borrowed renderers). This is the "define your own theme or skin" loop from the project's start.
  - Import and export for Tailwind and Mantine themes, so an existing brand comes in and a web team shares the same source.
- **Consequences:** Figma's `ext/*` convention becomes `custom/<set>/…` in the brand's own naming. Hand-written token sets still work for small cases.

### ADR-33 Skins never bundle fonts
- **Context:** the Material note asked whether to bundle Roboto, and the Carbon note bundled IBM Plex Sans. Fonts add hundreds of KB per app, and some can't be redistributed (Apple's SF Pro may not ship outside Apple platforms).
- **Decision:** no skin bundles a font. Every starter theme takes `fontFamily`, defaulting to the platform font (`CamoTypography.system()`); each skin note names the font for the authentic look, and the app adds it.
- **Consequences:** the font stays a brand decision in the theme (ADR-28). Tooling reports fonts a tokens file uses but the app doesn't have; it never adds font files.

### ADR-34 The web port (Later) is built as Web Components
- **Context:** Studio's web canvas and a web export need Camouflage on the web. Covering React, Vue, Svelte and Angular separately would be several ports.
- **Decision:** a Later third platform, **Camouflage for web**, built as framework-neutral **Web Components** (custom elements), with its own `web/` docs mirroring `base/`. Themes map to CSS custom properties (which cross the Shadow DOM), a nested provider becomes a wrapper element, and form fields use `ElementInternals`.
- **Consequences:** one web implementation for every framework. The `camo` generator gains a web target (CSS variables and a typed theme object), and Studio a web canvas.

### ADR-35 Camouflage builds what apps would borrow from Material
- **Context:** without a component, apps mix in Material widgets (a date picker first), which brings Material's look and theme into a Camouflage app. A `ThemeData`/`MaterialTheme` bridge was considered and rejected: the goal is to never need Material.
- **Decision:** the components apps would borrow in a first release move from Later to v1: **`CamoDatePicker`** (single and range, plus the `CamoCalendar` building block), **`CamoTimePicker`**, **`CamoStepper`**, **`CamoAccordion`**. No Material bridge package.
- **Consequences:** v1 = 40 component notes and 39 renderers. Core gains its first non-UI dependencies for dates: `kotlinx-datetime` (plus a small `expect`/`actual` for localized names, the first day of the week and the 12/24-hour setting) and Dart's `intl`. Pickers' forms (calendar or wheel; fields, dial or wheel) are theme choices (ADR-28).

### ADR-36 Publishing namespace is `com.srctool`
- **Context:** the Maven group was open between `org.srctool` (if the author could verify `srctool.org`) and `io.github.srctool`. The author bought **srctool.com** instead (verification in progress on 2026-10-02).
- **Decision:** Maven group `com.srctool.camouflage`, Kotlin package root `com.srctool.camouflage.*`, convention plugin ids `com.srctool.*`, the pub.dev verified publisher `srctool.com`, and the tokens schema under `https://srctool.com/`. If verification fails, the fallback group is `io.github.srctool.camouflage`.
- **Consequences:** only the `srctool { publishing { groupId } }` value would change on fallback. Sinew uses the same domain (`com.srctool.sinew`).

### ADR-37 Sinew's final shape, as Camouflage sees it
- **Context:** ADR-29 described Sinew as it was planned then ("generic `Response`/`PagingResponse` mapping, paging use cases, view state"). Sinew's own docs have since settled a different shape.
- **Decision:** nothing in Camouflage's contracts changes. `CamoPagedListState` stays a plain state with a `PagedError(message: String)`. The current description of Sinew, which supersedes the descriptive part of ADR-29:
  - Sinew's paging is a `Pager<T>` writing a `PagingState` whose `ViewState` is `Loading | Done | Failed` (no `Idle`). A list starts as `Loading` + `Initial`, so `CamoPagedList` shows its skeleton from the first frame.
  - Sinew's error messages are keys or backend text, rendered at display time. The glue (`sinew_camouflage`, which depends on `sinew_l10n`) renders the message with the app's localizer when it builds `CamoPagedListState`, so the list's error text follows the current language.
  - Sinew drops a list's items on refresh, so `PagedListTheme.refreshKeepsItems = true` isn't supported through Sinew's glue. Other sources can still use it.
  - The glue is `PagingState<T>.toCamo(localizer)`. Kotlin adds a `@Composable toCamo()`, and Flutter `toCamoOf(context)`.
- **Consequences:** none for Camouflage's code. The dependency rule is unchanged: Camouflage never depends on Sinew, and only `sinew_camouflage` knows both.
